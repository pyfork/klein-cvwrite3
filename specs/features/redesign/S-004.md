# Slice S-004: When a change adds a script that the allow-list does not allow, the developer sees the test suite fail and name the script and the file.

Feature: [brief](brief.md)
Slice: 4 of redesign

## Outcome
When a change adds a script that the allow-list does not allow, the developer sees the test suite fail and name the script and the file. Today one script exists, `app/static/upload.js`, loaded by `profile.html`. Addendum 15 allows a few more, each on the pages that use it (the home's switch, the drag-to-compare slider), and asks for a test that fails on any other.

## Rules

AC-84 Given `app/static/` and `fonts/` (the app serves both, at `/static` and `/fonts`),
      when the suite runs,
      then every script file in `app/static/` (a `.js` or `.mjs` file at any depth) must be named in the allow-list, in `tests/test_scripts_allowlist.py`, and no script file at all is allowed in `fonts/`; an `.svg`, `.html`, `.htm`, `.xhtml`, `.xht` or `.xml` file in either folder that holds a `<script` or an inline handler fails too. Any other fails the suite, and the failure names the file.

AC-85 Given the templates in `app/templates/` and every folder below it,
      when the suite runs,
      then every `<script>` tag in them is exactly `<script src="/static/NAME.js" defer></script>` (double quotes, no other attribute and no repeated one, no code inside; a `?v=` after the name is allowed; tag and attribute names in any letter case), and `NAME.js` is on the allow-list. An inline handler (`onclick=` and the like, however it is separated from the tag name or the attribute before it: a space, a slash or a quote) or a `javascript:` address anywhere in a template fails too. A template is named by its path under `app/templates` (`sub/page.html`), and the failure names it.

AC-86 Given an allow-list entry (its pages are paths under `app/templates`, so `profile.html` is not `sub/profile.html`),
      when a template that is not one of its listed pages loads the script, the suite fails and names the template and the script; and when an entry names a script file that does not exist, or a page that does not load it, the suite fails too (a list entry cannot go stale).

AC-87 Given an allow-list entry,
      when the list is read,
      then it says in words what the page does without the script (Addendum 15: every page works with scripts off); a script that moves anything also says what shows with scripts off or reduced motion. An entry with no such text, or no pages, fails the suite.

AC-88 Given the app as it is when this slice merges,
      when the suite runs,
      then the test passes, with `upload.js` on the list for `profile.html`. The test is plain standard-library `unittest`, finds the tree from its own path (`app/templates` and `app/static` above `tests/`), and exposes the list as a module-level dict `ALLOWED`: script path under `app/static` → `{"pages": {template file names}, "without": text}`. The suite's runner (`scripts/test.sh`, `unittest discover tests`) finds it with no change.

## Out of scope
- **A runtime `Content-Security-Policy` header for scripts:** Addendum 15 asks for a test, not a header; a header changes every response, so it is its own SHARED slice. Revisit in slice 6's plan (the first slice that adds a script), if the owner wants the runtime guard as well.
- **A script inside a partial template (`_packs.html`, `_prep.html`):** the list names the file that holds the tag, not the pages that include it, so "only on the pages that use it" is enforced per file. Revisit when a script is first put in a partial.
- **Other file types in `fonts/` and `app/static/`:** only the types listed in AC-84 are read. Revisit if the app serves another type that can run script, or a new folder.
- **HTML built in Python:** the test reads templates and static files; nothing in `app/*.py` builds a `<script` today (searched on 2026-11-03: none). Revisit if one appears.
- **The scripts themselves, and the no-script and reduced-motion behaviour of the pages:** slice 6 adds the first new script and its end state. This slice adds only the rule that each entry says what the page does without it.
- **The Screens line of `docs-public/project-rules.md`:** the owner's own change, before the first slice that adds a script (the plan's Owed list).

## Touch points
- `tests/test_scripts_allowlist.py`: new, the whole deliverable.
- `CHANGELOG.md`: one line.
- Nothing the app serves changes: no template, script, style or font, so `app/main.py`'s `APP_VERSION` stays and the stand-in pages under `acceptance/screens/` need no regeneration.
